# pi-go 目录索引

`go/` 的导航入口。回答"什么代码在哪里"，不解释"为什么这样设计"——后者见 [architecture.md](architecture.md)。

表格中的路径可以直接点击进入目录。状态取值：**已实现**（有代码和测试）、**部分**（骨架可用，能力不全）、**规划中**（目录尚不存在，仅记录意图）。

`config` 只依赖标准库，也不认识任何适配器：它负责回答"有哪些 provider 和模型、各自的凭据是什么"，不负责把它们变成请求。`api` 字段只是一个路由键，由 `cmd/atlas` 消费。插件也在这层读，而它同样只是"把文件读成声明"：`plugin.json` 能说"我有一组 skill 和几台 MCP 服务器"，说不了"跑这条命令"——`tests/config/run.sh` 用一条 import 守卫钉住这件事（不许 `os/exec`、`net`、`net/http`）。

`theme` 同样只依赖标准库：它把主题文件读成色值交出去，把色值变成样式是 `internal/tui` 的事。这条分界的用处是"十二个 token 齐不齐、拼错没有"能在没有终端的测试里回答，而 `tests/deps/run.sh` 仍可以是一条规则而不是一串例外。

```bash
./tests/run.sh          # 全部模块
./tests/run.sh sse      # 只跑指定模块
```

`run.sh` 用 `tests/*/run.sh` 自动发现模块，但新增模块仍要在上表登记（维护规则 1）。`guard_stdlib_only` 守的是硬约束而非偏好：`wire` 与 `sse` 一旦引入外部依赖，"内核能在空模块缓存里编译"的前提就没了。0.4.0 把这条边界改成按层划：`tests/deps/run.sh` 允许 `internal/tui` 与 `cmd/atlas` 引用第三方，其余 `internal/` 包一律不许，并且查的是依赖闭包，所以经由我们自己的包间接摸到第三方也会被抓到。`guard_no_imports` 守的是依赖方向：`provider` 与 `openai` 一旦能到达 `agent` 或 `tool`，分层就退化成注释。`guard_deps_allowed` 是它的宽松版：允许列出的 `pi-go/` 前缀，仍然禁止第三方包——`fs` 与 `shell` 合法依赖 `tool` 和 `wire`，但不该依赖别的工具，也不该引入 `go-gitignore` 之类的库；`session` 合法依赖 `wire`，但不该看见 `provider` / `tool` / `agent`；`rpc` 合法依赖 `app` / `session` / `wire`，但不该看见具体适配器。

新增包时先确定它指向哪一层。如果一条依赖箭头需要反向，说明分层划分有问题，不要加例外。

## 维护规则

1. **目录变化必须更新本文件。** 新增、删除、改名、移动目录，都要同步修改上表；这是索引能用的唯一前提。
2. **用命令核对，不要凭记忆。** 重新生成目录列表：
   ```bash
   find . -type d -not -path '*/.git*' | sort
   ```
   文件级清单：
   ```bash
   find . -type f | sort
   ```
3. **规划中的目录移到上表时补链接。** 不存在的目录一律不加链接，避免死链。
4. **描述写"职责"，不写"实现方式"。** 例如"宽松参数解码"是职责，"用 json.Decoder + UseNumber"是实现，后者属于 architecture.md。
5. **本文件管"在哪"，architecture.md 管"为什么"。** 同一事实只在一处展开，另一处指向它。
6. **状态只升不猜。** 没跑通测试的不写"已实现"。
